# Nexa Accounts

The standalone **sign-in and sign-up app** for Nexa. It lives in its own project and deployment so that changes to the main UI never touch the login page, and work on login never touches the main UI.

After a successful sign-in it sends the user **back to the app they came from** (the main UI, or any other Nexa app you allow).

## How the handoff works

No token ever appears in a URL. The API issues a one-time code, and the app that asked for the sign-in swaps it for a token.

```
 Main UI                         Accounts app (this project)                 API
    │  1. user clicks "Sign in"          │                                      │
    │  ── redirect ────────────────────▶ │  /login?return=<UI>/auth/callback    │
    │     (remembers a random `state`)   │         &state=<random>              │
    │                                    │  2. user submits the form            │
    │                                    │  ── POST /auth/login + redirectUri ─▶│
    │                                    │  ◀─ { code }  (one use, 60 seconds) ─│
    │  3. ◀── redirect ───────────────── │  <UI>/auth/callback?code=…&state=…   │
    │  4. checks `state`                 │                                      │
    │  ── POST /auth/exchange {code} ────────────────────────────────────────▶ │
    │  ◀─ { token, user } ───────────────────────────────────────────────────── │
    │  5. saves the session, opens the page the user wanted                     │
```

- **This app never sees or stores a token.** It only forwards the one-time code.
- The code works **once**, for **60 seconds**, and only for the exact return address it was issued for. Only a hash of it is stored.
- The API only issues codes for return addresses on its allowlist (`AUTH_ALLOWED_ORIGINS`), so nobody can use this page to send people, or their codes, to another site.
- `state` is generated by the main UI and checked on return, which stops someone from silently signing a visitor into the wrong account.

## Run it

```bash
npm install
cp .env.example .env.local   # then edit the two values
npm run dev                  # http://localhost:3001
```

| Variable | Description |
| --- | --- |
| `NEXT_PUBLIC_API_URL` | The Nexa API, including `/api`. |
| `NEXT_PUBLIC_DEFAULT_RETURN_URL` | Where to send people if the page was opened without `?return=`. Use the main UI's `/auth/callback`. |

Both are baked in at build time, so redeploy after changing them.

## Pages

- `/login` and `/register`: the forms. They read `?return=` and `?state=` from the address.
- `/`: sends visitors to `/login`, keeping the query.

## Set up the other projects

**API** (environment variables):
- `CORS_ORIGIN`: add **this app's address** next to the main UI's, comma separated, e.g. `https://search-engine-ui-eight.vercel.app,https://YOUR-AUTH-APP.vercel.app`. The browser calls the API from this app, so it must be allowed.
- `AUTH_ALLOWED_ORIGINS`: the apps people may be sent back to, **not** this one, e.g. `https://search-engine-ui-eight.vercel.app`. (If unset it falls back to `CORS_ORIGIN`.)

**Main UI** (environment variable):
- `NEXT_PUBLIC_AUTH_URL` = this app's address, e.g. `https://YOUR-AUTH-APP.vercel.app`. Redeploy the UI afterwards. If it is unset, the UI keeps using its own built-in login pages.

## Deploy

Deploy it like any Next.js app (Vercel works fine: it is a normal static-and-client app with no server state). Set the two variables above.

## Adding another app that uses it

1. Add the app's origin to the API's `AUTH_ALLOWED_ORIGINS`.
2. In that app, send people to `<this app>/login?return=<its callback address>&state=<random>`, and on return check the state and call `POST <api>/auth/exchange` with `{ code, redirectUri }`. The main UI's `lib/authRedirect.ts` and `app/auth/callback/page.tsx` are a working example.

## Not included yet

- It does not keep its own session, so every visit asks for the password again (no "single sign-on" between apps yet).
- No password reset, email verification or "sign in with Google".
